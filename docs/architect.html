webhook-platform architecture

Terms used everywhere

The code, the database and the dashboard all use these names.

org
The SaaS company using the platform (the tenant). Owns API keys, event types and consumers.
consumer
One of the org's customers, such as a shop. Identified by the org's own uid.
endpoint
A URL owned by a consumer, with a signing secret and the event types it subscribes to.
event
One thing that happened: org, consumer, type such as payment.paid, JSON payload.
message
One event addressed to one endpoint. This is the unit that gets delivered, retried and replayed.
attempt
One HTTP try for a message: request headers, response status and body, latency, error.

System map

Postgres sits above the processes because every process writes to it; Kafka sits below because the processes hand work to each other only through Kafka topics.

Modules and what each one owns

Five Go processes and one Next.js app. Whether the Go processes ship as five binaries or one binary with a role flag is an implementation choice; the boundaries below hold either way.

api

HTTP · stateless

The only HTTP entry point. Serves the ingest API for org backends, the REST API for the dashboard, and the built-in test receiver.

Auth
API key for /v1/*; JWT access + single-use refresh for the dashboard
Writes
event + outbox row in one transaction; dashboard CRUD; replay requests via the outbox
Reads
everything the dashboard shows, always scoped to the caller's org, keyset pagination
Redis
ingest rate limit per org, refresh tokens, API-key cache (M5)
Kafka
none
Scales
horizontally behind the ALB
On crash
in-flight requests fail; nothing accepted is lost, since 202 is only sent after COMMIT

relay

poller

Moves rows from the outbox table into Kafka, so the database write and the Kafka record can never disagree.

Loop
lock a batch FOR UPDATE SKIP LOCKED → produce → wait for acks → delete rows → commit
Produces
events (key consumer_uid); replay rows to deliveries
Scales
several relays side by side; SKIP LOCKED keeps them off each other's rows
On crash
rows unlock and are produced again; downstream dedupes
Watch
outbox backlog (alert)

dispatcher

consumer group

Fan-out. Turns one event into one message per enabled endpoint of that consumer that subscribes to the event type.

Consumes
events
Writes
messages, unique (event_id, endpoint_id), ON CONFLICT DO NOTHING
Produces
deliveries (key endpoint_id), then commits its offset
Redis
subscription cache per consumer (M5)
Scales
up to the partition count of events
On crash
re-reads the event, finds existing messages, produces them again: a possible duplicate send, never a loss

delivery-worker

consumer group · outbound HTTP

Makes the first attempt for every message and decides between success and the first retry tier.

Consumes
deliveries
Sends
signed POST through the SSRF-guarded client: private and metadata addresses refused at dial time, 15 s timeout, no redirects
Writes
delivery_attempts; message → succeeded or failed
Produces
deliveries.retry.1m on failure
Ordering
one endpoint = one partition, so first attempts arrive in order
On crash
offset not committed → message sent again; receivers dedupe on webhook-id

retry-worker

consumer group · outbound HTTP

Runs the delayed retries and moves exhausted messages to the dead-letter topic.

Consumes
deliveries.retry.1m, .10m, .1h, .6h
Waits
pauses a partition until record timestamp + tier delay; no busy loop
Produces
the next tier on failure; deliveries.dlq after .6h
Writes
attempts; message → succeeded or dead
Trade-off
retried messages may arrive after newer ones (ADR-0003)

web

Next.js App Router

The developer dashboard. Talks only to api; holds no business rules of its own.

Screens
API keys, event types, consumers and endpoints, event log, event detail with replay, test receiver controls
Data
TanStack Query; filters live in the URL; cursor pagination
Stack
shadcn/ui, Tailwind, next-intl, Vitest, Playwright

Backing services

PostgreSQL

durable

Source of truth for configuration, events, message status and attempts. Also the outbox that feeds Kafka.

Kafka

durable · KRaft

The delivery pipeline: ordering per key, consumer groups for scale, offsets for redelivery. Self-managed on EC2 in AWS (ADR-0005).

Redis

loss-tolerant

Only state that is shared between instances and safe to lose. If it is down, rate limits fail open and caches fall back to Postgres.

Prometheus · Loki · Tempo · Grafana

observability

Metrics, logs and traces with dashboards and alerts provisioned from /deploy/grafana. Same setup locally and on AWS.

    Observability

    One trace follows an event from the API request to the outbound HTTP call. The trace context rides in Kafka record headers between processes.

    Metrics to know

    • outbox backlog: rows waiting for the relay; grows when Kafka is down
    • consumer lag per group: is each stage keeping up
    • delivery success rate and attempt latency p50 / p95 / p99 per endpoint
    • retry-tier depth and DLQ count
    • ingest rate per org and 429 count

    Conventions

    • Logs are structured JSON (log/slog) and always carry trace_id.
    • API keys and signing secrets never appear in logs or spans.
    • Dashboards and alert rules live as files in /deploy/grafana; change them by PR, not in the UI.
    • Alerts start with consumer lag above threshold and a spike in failure rate.
